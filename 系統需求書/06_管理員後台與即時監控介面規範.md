# 06. 管理員後台與即時監控介面規範

本文件定義系統（Tunnel 匿名聊天）的管理員後台 (Admin Dashboard) 介面規範、即時監看機制、強制斷線 (Kill Switch) 與針對特定對話成員 (User A / User B) 的即時接管功能。

---

## 一、 管理員後台核心功能架構 (Admin Dashboard Architecture)

管理員後台為獨立的受保護介面（限制 `role = 'admin'` 存取），具備全系統 1對1 對話的實時監控與緊急干預能力，防止詐騙、洗錢或違規線下交易。

**權限登入機制 (Admin Access)**：
- 由於採全匿名 Auth 設計，系統預設所有新註冊使用者角色均為 `user`。
- 系統只檢查目前登入帳號的 `profiles.role`，只有已由資料庫擁有者預先授予 `admin` 角色的帳號可以載入管理介面。
- 瀏覽器端不得提供共用密碼、權限提升 RPC 或自行申請管理權限的入口。

```
[管理員後台面板 (Admin Dashboard)]
       │
       ├─► 1. 全域實時監控面板 (Live Chat Monitor) ──► 瀏覽目前所有活躍對話列表
       │
       ├─► 2. 緊急斷線開關 (Emergency Kill Switch) ──► [強制斷線] 按鈕 ──► 終止房間
       │
       └─► 3. 即時角色接管 (Takeover Controls) ─────► [接管 User A] / [接管 User B] ──► 踢出並替代
```

---

## 二、 即時監看與控制介面規範 (Interface Specifications)

### 1. 全域活躍對話監看與系統數據看板 (Active Matches & Live Metrics)
- **系統即時數據指標卡 (Live System Metric Cards)**：
  - **尋找配對中動態計數器 (Searching Queue Count)**：即時顯示「目前有 1,234 人正在尋找配對」（全站進行配對佇列比對的在線人數統計，此數據已從一般使用者前端隱藏，僅於管理後台呈現）。
  - **活躍對話房間數 (Active Matches Count)**：顯示當前全站正在進行 1對1 對話的房間總數 (`is_active = true`)。
- **對話列表視圖**：即時顯示目前全站 `is_active = true` 的所有對話房間。
- **卡片資訊顯示**：
  - `Match ID`（房間 UUID 縮寫與完整碼）
  - `對話雙方資訊`：顯示 User A（暱稱、性別、縣市）與 User B（暱稱、性別、縣市）
  - `聊天意圖 (Intent)`：如 心情抒發 / 靈魂拷問 / 純聊天
  - `進行時間 (Duration)`：這場對話已持續時間
  - `即時狀態`：正常對話中 / 已被接管 / 警示中
- **單一對話監看視窗 (Live Chat Window)**：
  - 點擊對話卡片後，右側彈出即時對話串流視窗。
  - 管理員可即時接收並閱讀 User A 與 User B 之間的最新 P2P / DB 訊息。

---


### 2. 強制斷線功能 (Emergency Kill Switch)
- **觸發按鈕**：位於對話卡片與監看視窗右上角之 **「🚨 強制斷線 (Terminate Match)」** 按鈕。
- **應用場景**：當管理員監看到非法交易（如毒品、洗錢、詐騙匯款）時，無須接管對話，可直接秒級終止對話。
- **執行動作**：
  1. 呼叫 SQL 預寫程序 `terminate_match_by_admin(p_match_id, p_reason)`。
  2. 資料庫將 `matches.is_active` 改為 `FALSE`，並寫入 `ended_reason = 'admin_terminated'`。
  3. 雙方前端瞬間接收斷線信令，視窗關閉並彈出通知：「**該對話因涉嫌違反平台安全規範，已被系統強制終止。**」
  4. 雙方 `profiles.status` 自動解鎖還原為 `online`（或針對違規者進行 Ban 帳號處置）。

---

### 3. 無感即時接管功能 (Stealth Takeover)
- **控制按鈕配置**：在對話監看視窗頂部，分別配置兩個醒目的操作按鈕：
  - **`[ 👤 接管 User A ]`** 按鈕
  - **`[ 👤 接管 User B ]`** 按鈕

#### 隱蔽接管核心原則 (Stealth Principles)：
管理員接管的目的在於**蒐證與釣魚防範惡意/違法交易**（如詐騙、毒品、違法線下交易）。接管過程必須達到**「對手完全無感、原使用者即刻隔離」**，確保對方不會覺察原本的使用者已被管理員接管。

#### 操作流程與系統反應（以接管 User B 為例）：

```
管理員點擊 [接管 User B] 
   │
   ├─► 1. 執行 admin_takeover_session(match_id, user_b_id, reason) ─► 設定 matches.is_taken_over = TRUE
   │
   ├─► 2. 對手 (User A) 體驗 ─►【完全無感 + WebRTC 毫秒降級 (Stealth Fallback)】
   │      - 當 User B 被切斷連線導致 WebRTC P2P Data Channel 物理中斷時，
   │        User A 前端立刻在毫秒內 (< 50ms) 自動切換至接收 Supabase Realtime 資料庫訊息流。
   │      - 對話 UI 畫面、狀態標籤、對方暱稱與頭像保持 100% 一致，絕不彈出任何中斷提示。
   │      - 接收管理員發送的訊息時，完全呈現為原本 User B 的訊息內文。
   │
   ├─► 3. 被接管者 (User B) ─►【雙重擬真隔離 (Silent UI Mock)】
   │      - Supabase RLS 立即鎖定 `matches.is_taken_over`，徹底阻斷 User B 的 API 訊息寫入。
   │      - 被接管者前端 UI 保持「發送中」或「成功送出」之模擬假象，使其誤以為對方尚未回覆，完全無法察覺已被後台接管。
   │      - RLS 權限切分，User B 僅能查看接管時間點 (takeover_at) 前的歷史對話。
   │
   └─► 4. 管理員 (Admin) ─►【無縫身分接管 (Full Takeover)】
          - 管理員後台監看視窗解鎖輸入框與發送按鈕。
          - 呼叫 `admin_send_takeover_message` 程序，以原本 User B 的 `sender_id` 與身分發送訊息給 User A。
          - 支持即時查看 User A 發給 User B 的所有回應，達成完全無縫接管聊天。

```

- **權限與安全審計**：
  - 接管觸發時，管理員需選擇或輸入「接管原因」（如：疑似違規交易巡查、收到檢舉介入）。
  - 所有接管操作無死角記錄於 `admin_takeovers` 稽核日誌表中。

---

### 4. 檢舉審核與信譽評分佇列 (Report Review & Credibility Queue)
- **檢舉快照審查 (`context_snapshot`)**：後台自動調閱舉報單號附帶的最近 10 條對話快照內文，管理員可一目瞭然釐清違規事實，無需全表檢視對話。
- **信譽分處理 (Reputation Action)**：
  - **確認違規**：管理員一鍵發動 `Ban User`（觸發 JWT 1秒踢出與 P2P 斷開）。
  - **惡意檢舉倒扣與反向處置**：若判定舉報為誣告，管理員點擊 `Dismiss (誣告)`，系統自動扣除舉報者 `reputation_score` 30 分，並對惡意舉報者施以 **24 小時反向禁言**。

## 三、 後台統計與營運數據看板 (Analytics Dashboard)

為了協助管理者掌握平台活躍度與營運狀況，管理員後台內建了「Analytics」分頁，提供即時的視覺化營運數據。

### 1. 核心數據指標 (Key Metrics)
- **總配對數 (Total Matches)**：系統歷史以來的成功配對總數。
- **活躍用戶數 (Active Users)**：當前處於配對狀態中（`is_active = true`）的用戶總數推估。
- **今日檢舉數 (Total Reports)**：系統已記錄的檢舉案件數，供後台巡查參考。

### 2. 視覺化呈現 (Visualizations)
- **流量與趨勢圖 (Traffic Overview)**：運用純 HTML/CSS 刻出 RWD 直方圖表，提供不依賴外部大型套件的高效能視覺動畫，呈現系統活躍狀況。
