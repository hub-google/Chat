# 03. 資料安全與權限控制規範 (詳細展開版)

在「1000 人同時在線」且具備「匿名性」的系統中，安全性的核心在於如何平衡「隱私保護」與「惡意行為防範」。本規範詳細定義了系統的安全性邊界與權限實作細節。

---

## 一、 Supabase RLS (Row Level Security) 深度定義

這是系統防禦的最前線。所有資料庫請求必須經過 RLS 校驗，嚴禁透過服務端密鑰（Service Role Key）在前端執行操作。

### 1. `profiles` 表權限
- **查看權限 (SELECT)**：
  - 使用者可隨時讀取自己的 Profile。
  - 對於其他使用者：僅當兩者處於同一個 `match_id` 且 `matches.is_active` 為 true 時，允許讀取對方的選填資料（如 `gender`, `age`, `city`, `job`, `bio`）。**嚴禁直接暴露精確 GPS 經緯度 (`lat`, `lng`) 與 `id` 以外的敏感 metadata。**
- **修改權限 (UPDATE)**：
  - `check (auth.uid() = id)`：僅限本人修改自己的資訊與地理位置。

### 2. `matches` 表權限
- **查看權限 (SELECT)**：
  - `auth.uid() = ANY(participants)`：只有參與者能看到這份配對紀錄。
- **修改權限 (UPDATE)**：
  - 僅允許參與者將 `is_active` 改為 `false`（即按下「離開」按鈕），且此動作觸發後不可逆。

### 3. `messages` 表權限 (熱快取層)
- **寫入權限 (INSERT)**：僅允許前端透過 `bulk_insert_messages` 預寫程序或受驗證的 `auth.uid() = ANY(participants)` 進行批次寫入。
- **讀取限制 (SELECT)**：`auth.uid() = ANY(SELECT participants FROM matches WHERE id = match_id)`。
- **自動清理權限 (DELETE)**：僅限系統服務帳號 (Service Role Key) 或定時 Cron 腳本清理過期對話，前端完全禁止執行 DELETE 操作。

### 4. 即時封鎖生效與 JWT 空窗期防護 (Immediate Ban & RLS Enforcement)
- **問題防禦**：JWT 的 Valid Period 為 3600 秒。當管理員觸發「緊急強制封鎖」帳號時，已簽發的 Token 無法在用戶端強制作廢。
- **RLS 即時校驗防線**：所有 Supabase RLS 策略（包含 `profiles`, `matches`, `messages`, `matching_pool`, `chat_reports`）強制整合 `EXISTS (SELECT 1 FROM users WHERE id = auth.uid() AND is_banned = FALSE)` 檢查。
- **秒級防護效果**：一旦管理員標記封鎖 (`is_banned = TRUE`)：
  1. **DB 阻斷**：攻擊者即使持有合法 JWT，打 Supabase API 發起存取與寫入將於 **< 1 秒內** 被 RLS 拒絕 (HTTP 403 / Permission Denied)。
  2. **Realtime 踢出廣播**：系統透過 Supabase Realtime 對該用戶廣播 `FORCE_LOGOUT` 訊號，前端接收後清空 LocalStorage Token 並導向封禁宣告頁面。
  3. **P2P Channel 切斷**：聊天對手前端接收到對手被封禁事件，自動關閉 Data Channel 避免繼續接收不當封包。

## 二、 隱私保護、地理位置資安與身分識別規範

### 1. GPS 經緯度隱私保護、模糊化與跨裝置定位資安 (GPS Privacy & Cross-Device Security)
- **絕對不暴露精確座標**：使用者的原始 GPS 座標 (`lat`, `lng`) 僅用於資料庫內部的距離算式 `haversine_distance` 進行配對篩選，**絕不直接透過 API 傳送給聊天對手**。
- **前端模糊距離渲染**：前端經由伺服器 RPC 計算後僅取得「概略距離」（如「距離約 3.2 公里」或「遠距離對象」），防止極端分子透過三角測量法推算使用者精確住所或位置。
- **手機與電腦跨裝置定位安全性 (Mobile GPS & Desktop IP Fallback)**：
  - **手機端**：原生 GPS 經緯度寫入前強制經過加鹽模糊偏移（保留小數點後 2 位，約 1.1 km 範圍），確保隱私最高安全性。
  - **電腦端**：無 GPS 晶片時自動降級調用伺服器端 IP 網段地理位置，不存取任何個人私人隱私敏感權限。
- **Build Timestamp 免 Ctrl+F5 資安校驗**：快取更新檔傳送包含 HMAC 簽署 Hash，防止中間人攻擊或偽造版本號發動惡意網頁重載。

### 2. 數位指紋、IP 風控記錄與 Google reCAPTCHA 防爆破 (Device Fingerprinting & Anti-Bot Engine)
- **瀏覽器數位指紋 (`device_fingerprint`) 與同瀏覽器多頁籤同步 (Cross-Tab Sync)**：
  - 前端利用裝置與瀏覽器硬體特徵（Canvas 渲染特徵、WebGL 繪圖參數、AudioContext、Screen 螢幕解析度、系統時區語言、UserAgent）進行加鹽單向哈希 (`SHA-256`)，生成唯一「裝置數位指紋」。
  - **同瀏覽器多頁籤同步 (`BroadcastChannel`)**：同一瀏覽器開啟多個分頁或視窗時共用 `LocalStorage` 與 Guest Session UUID。系統透過 `BroadcastChannel` 與 `storage` 事件進行全分頁狀態同步。所有分頁同步顯示同一配對狀態與聊天對手，避免重複佔用配對池。
- **風控 IP 記錄 (`last_ip`) 與 跨帳號關聯判別 (Cross-Account Correlation)**：
  - 後端 API 與 Supabase 在請求入口處擷取用戶連線 IP (`X-Forwarded-For` / `CF-Connecting-IP`)，記錄於風控稽核日誌與 `profiles` 資料表中。
  - **機器人農場警報 (Bot Farm Alert)**：當同一 IP 在短時間內切換多個 `user_id` 發起檢舉或刷配對時，自動將該批帳號之舉報計數全部設為無效 (`is_valid = false`)。
- **Google reCAPTCHA 風控觸發機制 (Bot & Spam Protection)**：
  - **防多開/開無痕刷人 (IP Active Sessions > 3)**：當同一 IP 底下擁有 **> 3 個獨立 Session（如開啟無痕模式、不同瀏覽器或腳本多開）** 同時處於配對/聊天狀態時，第 4 個及之後發起配對的獨立 Session 強制跳出 Google reCAPTCHA 驗證，通過後方可加入配對佇列。
  - **高頻發文/廣告刷版防禦 (High-Frequency Messaging Limit)**：若單一視窗於 **30 秒內發送 > 30 條訊息** 或短時間發送重複連結/網址，系統暫停該 Session 發言權，並強制要求完成 Google reCAPTCHA 驗證碼解鎖（設定 30 秒 30 條之寬鬆門檻，既能攔截機器人秒射廣告，又可完美避免一般人類聊天激動時遭到誤殺）。
  - **秒進秒退洗人防禦 (Rapid Match-and-Leave Limit)**：若單一 Session **連續 3 次配對成功後 3 秒內按下離開**，系統強制施加 15 秒配對冷卻 (CD)，且下一次配對需通過 Google reCAPTCHA 驗證。

### 3. 全匿名身份管理與 Google Drive 備份資安
- **Guest Login**：支援匿名登入，系統自動分配一組臨時 UUID，不需設定暱稱。
- **Google Drive 冷備份資安**：
  - **傳輸與靜態加密**：上傳至 Google Drive 的 JSON 備份檔必須在記憶體中進行 AES-256 加密。
  - **最小權限原則**：歸檔腳本使用專屬的 Google Service Account（由 GitHub Actions / Cloudflare Workers Secrets 注入），存取範圍嚴格限制於 Tunnel 專用資料夾，絕不暴露密鑰至前端。
  - **去識別化**：JSON 存檔內容不包含 IP、GPS 精確經緯度或個資，僅保留對話內文、房間 ID 與隨機生成的 User UUID。

## 三、 風控與反垃圾系統 (Anti-Abuse Engine)

為了應對 1000 人同時在線可能產生的洗版、惡意騷擾與女巫攻擊 (Sybil Attack / Bot Farm)，採用以下分層防禦：

### 1. 流量限制與防騷擾機制 (Rate Limiting)
- **配對頻率 (Edge Function 控制)**：單一使用者 UUID 或單一裝置數位指紋 (`device_fingerprint`) 1 小時內不得發起超過 30 次成功的配對與主動離開行為（防止惡意刷人）。超過限制者，後端自動封鎖配對功能 5 分鐘。
- **發言頻率與接收端熔斷 (Receiver-side Circuit Breaker)**：由於訊息走 WebRTC P2P 傳輸，惡意使用者可能竄改瀏覽器客戶端程式碼以繞過發射端限制。因此，系統防護重心嚴格落實於 **Data Channel 接收端**。接收端 Client 會即時計算進站訊息頻率，若偵測到對方 10 秒內發送超過 15 則訊息，接收端將瞬間啟動流量熔斷機制，主動中斷 P2P 連線並拋棄後續封包，徹底防止 WebRTC 訊息洪水攻擊。

### 2. 客戶端檔案壓縮與頻寬安全 (Client-side Compression)
- **圖片壓縮**：為避免使用者傳送過大圖片（如 5MB 以上原圖）導致上傳失敗或拖慢連線體驗，系統使用 HTML5 `Canvas` API 在前端將圖片重新繪製並等比例壓縮，最大寬度限制為 `1024px`，期望將圖片大小縮減至 `1MB` 以內，再上傳至圖床。

### 3. 關鍵字自動過濾與系統警示 (Auto-Moderation)
- **前端本地字典**：雖然系統高度保障隱私，但為了防範詐騙與違法線下交易，前端內建了風險關鍵字庫（包含但不限於：「匯款」、「點數」、「投資」、「買賣」、「詐騙」、「援交」）。
- **即時比對與警示**：一旦偵測到敏感字詞，前端 UI 會自動彈出紅色系統警語提醒使用者防範詐騙。
- **靜默風險標記**：該行為不阻擋訊息送出（避免打草驚蛇），但會背景靜默觸發系統警報 (`chat_reports` 資料表)，將該場對話標記為「高風險對話」，供管理員在後台優先監控。

### 4. 舉報防惡意攻擊與滾動時間窗懲罰機制 (Anti-Malicious Reporting & Ban Engine)

為了徹底防範惡意檢舉、霸凌與機器人刷檢舉攻擊，系統落實以下防衛邏輯：

- **(1) 檢舉有效性門檻校驗 (Pre-qualification)**：
  - **頻率上限與對話門檻**：每位使用者 1 小時內最多發起 **3 次檢舉**；且**對話時間須 > 5 秒**或**雙方至少傳送過 1 則訊息**。配對 0 秒即秒離者點擊檢舉自動無效化。
  - **自動附帶 10 條對話快照 (`context_snapshot`)**：前端發起檢舉時，必須自動打包該對話最後 10 條訊息快照一併寫入 `chat_reports` 表，供管理員後台審查，無視實質證據之匿名檢舉自動視為無效。
  - **舉報者誠信分與身分過濾**：註冊未滿 10 分鐘、誠信分低於 50 分，或同 `device_fingerprint` / 同 `last_ip` 的多個分身帳號發起的檢舉，其檢舉計數自動設為無效 (`is_valid = false`)，不觸發自動懲罰，僅留存日誌待查。
  - **單場唯一**：每位使用者在同一次 `match_id` 中僅能檢舉一次。

- **(2) 24 小時滾動時間窗 (Rolling 24-Hour Window)**：
  - 系統**嚴禁使用終身累積計數**。所有懲罰門檻皆基於**「最近 24 小時內」**所接收到的「**不重複且有效高誠信使用者/指紋**」檢舉數量。

- **(3) 分級自動處置與人工審核 (Tiered Enforcement)**：
  - **初級門檻 (24hr 內被 3 位有效用戶舉報)**：系統自動冷卻，暫時禁止配對 **1 小時**。
  - **中級門檻 (24hr 內被 6 位有效用戶舉報)**：暫時凍結配對 **24 小時**，並自動發送警報將該用戶及歷史對話送入管理員後台 **「高優先審核佇列 (Pending Review Queue)」**。
  - **高級門檻與永久封鎖原則**：**系統嚴禁 100% 無人化自動永久封鎖**。永久封鎖必須由管理員於後台審閱對話日誌後人工執行。若系統於極端狀況自動觸發封鎖（如 24hr 內 > 12 位高誠信帳號舉報），亦須保留申訴管道與管理者復核機制。

- **(4) 惡意舉報反向懲罰 (Anti-Abuse Penalties & 24hr Ban)**：
  - 系統維護使用者「誠信分 (Reputation Score)」（初始 100 分）。
  - 若某使用者惡意亂檢舉（經管理員判定 Dismissed/誣告），每次倒扣誠信分 30 分。當誠信分 < 50 分時，其發起檢舉完全失去效果；經查為惡意檢舉者，系統自動實施 **24 小時反向禁言** 處分。

## 四、 身份驗證安全 (Auth Security)

- **JWT 強化與即時撤銷**：使用 `RS256` 簽署協議，Token 過期時間設定為 `3600秒`，並開啟 `Refresh Token` 滾動更新機制。配合 RLS 層 `is_banned()` 校驗，實現 Token 尚未過期時仍能實時硬性封鎖。
- **CSRF 防護**：所有 API 請求強制要求正確的 `Origin` 與 `Referer` Header，防止跨站請求偽造。
- **XSS 防護**：前端渲染訊息時強制執行 HTML Escape，嚴禁使用 `dangerouslySetInnerHTML`。

### 五、定位拒絕與距離資料安全（2026-08 修訂）

- 使用者同意瀏覽器定位時，以 GPS 座標進行配對距離計算。
- 使用者拒絕、逾時或裝置不支援定位時，仍允許配對，改用 IP 地理資料的近似經緯度；若 IP 定位也不可用，距離視為未知並允許進入漸進式擴圈。
- 對方只能讀取 `matches.distance_km`，永遠不得取得另一方原始經緯度。
- IP 定位僅保證國家／區域／城市等近似層級，不得宣稱可精準定位行政區、道路或門牌。
