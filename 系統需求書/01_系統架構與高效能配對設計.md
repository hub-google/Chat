# 01. 系統架構與高效能配對設計 (詳細展開版)

本文件針對「1000 人同時在線 (CCU)」的業務場景，深度解析系統的底層架構、配對邏輯演算法以及效能優化方案。

---

## 一、 核心技術架構 (Technical Architecture)

為了確保高併發下的低延遲與高可用性，採用以下架構：

### 1. 前端：Next.js / React (現階段部署：GitHub Pages / 預備 Cloudflare 相容架構)
- **部署模式**：全靜態匯出 (Static Export)。現階段**僅部署至 GitHub Pages** 進行開發測試與營運，伺服器主機成本 $0。
- **雙平台預備架構**：所有程式碼與環境變數注入格式（`.env` / Secrets）於開發初期即完成相容性規範，未來若需發布至 Cloudflare Pages 無需修改任何程式碼。
- **狀態管理**：使用 `Zustand` 處理輕量級全域狀態（配對狀態、佇列訊息快取）。
- **即時通訊**：採用 **WebRTC P2P** 傳輸通道。僅在配對階段以 Supabase Realtime 進行短暫信令交換 (SDP/ICE)，配對成功即切為雙向 P2P 直連，達成 $0 頻寬費。
- **PWA (漸進式網頁應用程式) 支援**：提供 `manifest.json` 與 `sw.js` (Service Worker)，讓使用者能在手機或電腦上將網頁「安裝」至桌面，獲得無網址列、全螢幕的原生 App 體驗，並支援離線基礎快取防護。

### 2. 熱資料快取層 (Hot Cache)：Supabase PostgreSQL
- **定位**：作為 24 小時動態滾動快取池。
- **寫入機制 (即時非同步 + 隊列重試)**：
  - **即時發送**：訊息產生時，背景立即發送 Supabase API 寫入，無須等待定時器。
  - **自動降級隊列 (Fallback Queue)**：若因高併發尖峰導致單次寫入失敗，前端自動將訊息納入 `retry_queue`，並排定 1 秒後打包重試，確保在高壓下 100% 零遺失。

### 3. 冷資料永久庫 (Cold Archive)：Google Drive (2TB 雲端硬碟)
- **歸檔機制 (00:00 上傳 + 軟刪除標記)**：每日凌晨 00:00 透過 **GitHub Actions Scheduled Workflows** 或 **Cloudflare Workers Cron** 自動觸發後端排程腳本（金鑰安全存放在後端 Secrets，零成本且絕不暴露至前端），將 Supabase 當日所有對話紀錄打包成加密 JSON 檔，上傳至 Google Drive 永久封存。
- **安全清理機制 (軟刪除與 7 天保留緩衝期)**：備份確認成功後，**嚴禁立即執行物理刪除或 `TRUNCATE messages`**（防範 GDrive API 假性成功或 Timeout 導致熱資料永久遺失，並避免 PostgreSQL 獲取強制的排他鎖 `ACCESS EXCLUSIVE LOCK` 引發併發崩潰）。系統執行 **軟刪除標記 (`UPDATE messages SET is_archived = TRUE, archived_at = NOW() WHERE created_at < CURRENT_DATE`)**，並保留 **7 天資料緩衝期**。物理清理改由每日 04:00 非尖峰時段之排程執行 (`DELETE FROM messages WHERE is_archived = TRUE AND archived_at < NOW() - INTERVAL '7 days'`)，確保線上寫入零影響且資料 100% 安全。

### 4. 圖床與檔案儲存：ImgBB 主圖床 (透過根目錄 `.env` 讀取金鑰)
- **零容量佔用架構**：圖片上傳全面使用 **ImgBB (主圖床)** API。Supabase 僅需儲存圖片外鏈 URL (`messages.content` 儲存 URL 文字)，絕不大爆 Supabase Storage 儲存空間（徹底解決 1GB 額度限制）。
- **環境變數存取規範 (.env 參考防護)**：
  - 開發與執行時**必須讀取專案根目錄的 `.env` 檔案**（變數名稱：`IMGBB_API_KEY`, `IMGBB_UPLOAD_URL`, `NEXT_PUBLIC_IMGBB_API_KEY`）。
  - 嚴禁於前端或原始碼中寫死 (Hardcode) 任何敏感 API Key，必須一律自 `.env` 或環境變數抽象層（如 `lib/env.ts`）取得，避免金鑰外洩。

### 5. 免 Ctrl+F5 快取無感即時更新架構 (Live Version Stamp & Cache-Busting Engine)
- **避免硬快取卡版問題**：網頁版隨時更新改版時，為防止使用者瀏覽器快取（Stale Cache）導致仍運行舊版程式或需要手動按 `Ctrl+F5` 重整，系統建置以下機制：
  - **建置時間戳記號碼 (Build Timestamp Injection)**： Next.js 於靜態匯出建置時，自動於全站 HTML/JS Asset 注入 `NEXT_PUBLIC_BUILD_TIMESTAMP`（格式如 `20260730_1240`）與 Build Hash。
  - **HTML Cache-Control 防護 Header**：頁面入口 `index.html` 設定 HTTP 標頭 `Cache-Control: no-cache, no-store, must-revalidate, max-age=0`，確保瀏覽器開啟網頁時必定向 Server 驗證 HTML 最新版本。
  - **背景版本輪詢與靜默重載 (Silent Version Polling)**：前端每 5 分鐘透過微型 JSON 檢查伺服器端最新版本標籤；若偵測到 Server 已發布新 Build Timestamp，前端會在用戶「非對話狀態/閒置期」自動靜默更新資源，達成本地零感知、全網隨時開啟即最新版。

## 二、 核心業務邏輯與配對機制

### 1. 單一對話視窗與跨頁籤狀態同步 (Single-Active-Session & Cross-Tab Sync)
- **1對1 單對話視窗約束**：每個使用者同時只能開啟一個對話視窗進行配對與聊天。當使用者處於 `chatting` 狀態（即 `matches.is_active = true`），系統禁止該使用者發起新的配對請求，直到點擊「離開/結束對話」退出當前房間。
- **同瀏覽器多頁籤狀態同步 (`BroadcastChannel`)**：
  - 同一瀏覽器開啟多個視窗/分頁時，共用 `LocalStorage` 與同一 Session ID。
  - 系統採用 `BroadcastChannel` API 與 `storage` 事件進行全分頁動態同步：分頁 A 發起配對或進入房間時，分頁 B/C 自動同步切換為相同狀態與同一對手，避免重複佔用配對池。
- **對話 UI 按鈕切換邏輯**：
  - **配對搜尋中 (`pairing`)**：頁面顯示 **「取消搜尋 (Cancel Searching)」** 按鈕。
  - **配對成功聊天中 (`chatting`)**：頁面顯示 **「離開對話 (Leave Chat)」** 按鈕。
  - **離開對話後 (`ended`)**：頁面顯示 **「重新配對 (Match Again)」** 按鈕。
- **對話場次 UUID 綁定 (Session UUID)**：每次配對成功均生成唯一的 `match_id` (UUID)。全系統訊息 (`messages`) 強制綁定 `match_id`，確保精確紀錄「這場對話是誰與誰聊 (`participants`)、何時聊、聊了什麼內容」。

### 2. 徹底匿名與地理距離配對引擎 (Intent & Distance-based Engine)
- **極速秒配原則 (Zero-Filter Friction for Speed)**：
  - **唯一可篩選條件：僅有「距離」**。使用者在前端僅能選擇「距離模式」（拉條控制），**嚴禁**讓使用者設定性別、年齡或話題等硬性篩選條件，避免因過度過濾導致配對池過小、使用者長時間等待。
  - **個人資訊與開場喊話 (Profile & Opening Message)**：使用者可在首頁直接選填性別、年齡、居住城市、自介標籤與「開場喊話」。這些資料**不參與剛性過濾**，但在配對成功（`match_id` 生成）並建立連線後，系統會於聊天室頂部以資訊卡片形式展示對方的資料供破冰參考，同時**自動將開場喊話作為第一則訊息送出**。
- **手機 (Mobile) 與電腦 (Desktop) 跨裝置定位適應**：
  - **手機版**：優先調用 HTML5 Geolocation 原生 GPS 模組，取得高精度經緯度。
  - **電腦版**：若硬體無 GPS 晶片，系統自動平滑降級為 IP Geolocation（經緯度預估）或允許手動選取城市，確保電腦使用者體驗不受限。
- **配對核心權重**：`Distance Mode (距離半徑/越遠越好)` ➔ `Queue Join Time (先到先配)`。
- **高併發 RPC 封裝與佇列機制**：
  - **非同步佇列寫入**：前端點擊配對後將經緯度、距離模式寫入 `matching_pool` 表並發送 4 秒心跳（附帶 `last_ping_at`）。
  - **RPC 預處理程序**：配對查詢封裝於 PostgreSQL RPC `fn_match_user()` 中，採用 `SELECT FOR UPDATE SKIP LOCKED` 與 Haversine 算式在 10ms 內完成近距離或越遠越好鎖定。

### 3. 三階段動態距離擴張配對策略 (Graceful Distance Expansion)
為了確保極致的配對速度，配對邏輯僅根據等待時間動態擴張距離限制：
- **階段 1 (0-10秒)**：嚴格限制於使用者設定之距離半徑（如 5km 內）或「越遠越好」模式（強制確保雙方距離至少 >= 50km，防止近距離秒配問題）。
- **階段 2 (10-30秒)**：若為近距離模式，自動擴大距離半徑；若為越遠越好模式，擴大搜尋最遠等待者。
- **階段 3 (30秒以上)**：全域解鎖距離限制，只要有任何離線狀態正常的線上使用者即刻完成配對，達成零卡頓極速體驗。

### 4. 管理員「雙向極致無感即時接管」與 WebRTC 無縫降級機制 (Admin Takeover & WebRTC Fallback)
為了及時防止惡意詐騙、違規線下交易或騷擾行為發生，系統提供管理員實時對話監管與接管功能：
- **切斷被接管用戶連線與防發言 (RLS API 封鎖)**：管理員觸發 `admin_takeover_session` 後，系統在 `matches` 資料表設定 `is_taken_over = TRUE`。Supabase RLS 策略立即封鎖被接管者 (`target_user`) 的發言與讀取權限（即使其使用原始 JWT 呼叫 API 寫入亦回傳 403）。
- **被接管者靜默偽裝 (Silent UI Mock)**：被接管者前端 UI 保持訊息「發送中」或「成功送出」之模擬假象，使其以為對方只是不及時回覆，完全無法察覺自己已遭後台接管，防範其驚覺被抓後銷毀證據。
- **聊天對手 (User A) 毫秒級無感降級**：管理員切斷被接管者 P2P 連線時，User A 前端偵測到 P2P Data Channel 斷線瞬間（< 50ms），自動無縫切換為接收 Supabase Realtime 資料庫訊息流，無任何斷線或接管警告 UI。
- **管理員無縫代打**：管理員以被接管者身份發言，訊息經由 Supabase DB 寫入並透過 Realtime 串流推送給 User A，達到 100% 雙向無感接管。
- **接管稽核日誌**：系統自動寫入 `admin_takeovers` 資料表，記錄接管時間、管理員 ID、被接管使用者 ID 及原因以供安全審計。

### 5. 話題卡與分類題庫系統 (Topic Cards System)
為了提高對話互動率並降低尬聊：
- **分類與題目結構**：資料庫獨立建立 `topic_categories`（話題分類表）與 `topic_cards`（話題卡片題庫表）。
- **隨機與主動抽卡**：使用者在配對前可勾選偏好的話題分類，對話中可隨機觸發破冰話題卡（如：抒發心情、靈魂拷問、趣味幻想等）。

## 三、 資料庫效能與並發優化

### 1. 索引策略 (Indexing Strategy)
針對 1000 人 CCU 產生的海量查詢，必須建立精準索引：
- **`pairing_queue` 心跳與意圖索引**：`(intent, last_ping_at)`，支援高效篩選活躍配對請求。
- **`matches` 陣列 GIN 索引 (`USING gin (participants)`)**：解決 RLS 權限與場次查詢依賴 `auth.uid() = ANY(participants)` 引發全表掃描 (Sequential Scan) 的致命效能瓶頸。
- **`profiles` 狀態索引**：對 `status` 建立索引，方便監控系統統計在線人數。

### 2. 連線池管理 (Connection Pooling)
- 1000 名使用者同時操作時，資料庫連線數會迅速耗盡。
- **解決方案**：透過 Supabase 內建的 **Supavisor / PgBouncer**。
  - 將前端頻繁的短連線轉換為長連線池，確保資料庫不會因為頻繁建立/中斷 TCP 連線而崩潰。

## 四、 即時通訊與冷熱資料流設計 (Tunnel 2.0)

### 1. WebRTC P2P 通訊與隱私傳輸 (P2P Architecture & Privacy)
- **信令交換**：配對時透過 Supabase Realtime 交換 SDP/ICE 候選者，連線成立後即刻斷開，釋放連線數。
- **雙向傳輸 (文字與圖片)**：對話文字與多媒體直接在兩端瀏覽器 P2P 傳送，延遲最低且 0 頻寬花費。
- **隱私防護與 Candidate 過濾**：維持純 WebRTC P2P 傳輸（$0 頻寬成本極致化），前端限制 Candidate 種類，遮蔽本機 LAN 區域網路 IP，防範 IP 資訊進一步曝露。

### 2. 熱資料即時寫入、雙狀態追蹤與 sendBeacon 限制防護 (Instant Write & SendBeacon Guard)
- **即時非同步寫入**：使用者送出訊息時，除了透過 WebRTC P2P 傳給對方，前端同時發起非同步 `INSERT` 指令寫入 Supabase，達到對話即時入庫。
- **P2P 與 DB 雙狀態追蹤 (Dual Status ACK)**：前端訊息狀態區分「對方已接收 (WebRTC Data Channel ACK)」與「伺服器已存檔 (Supabase DB INSERT Response)」，避免兩端狀態與資料庫持久化異步產生的認知誤差。
- **接收端嚴格流量熔斷 (Receiver-side Circuit Breaker)**：防止惡意使用者竄改前端 Client 程式碼繞過 15 則/10 秒發言限制並發動 P2P 洪水攻擊。系統在 Data Channel 接收端實作嚴格熔斷檢測，若單一 Data Channel 在 10 秒內接收超過 15 則訊息，接收端強制熔斷連線、拒絕渲染並觸發安全回報。
- **高併發衝擊防禦與 sendBeacon 離線退列保護**：
  - 前端監聽 `visibilitychange` 與 `beforeunload` 事件，當使用者划掉分頁或關閉視窗時，自動發送 `navigator.sendBeacon` 將自己從 `pairing_queue` 中刪除，避免留存離線殭屍。
  - Payload 嚴格限制在 40KB 以內。若佇列超過大小或包含圖片 (Base64/DataURL)，前端自動將多媒體降級剝離（僅發送內文與元資料），且若仍有未同步大檔，於 `beforeunload` 彈出警告 UI 阻擋提示（「尚有資料未同步至伺服器」），防範請求被瀏覽器靜默拋棄。

### 3. 每日 Google Drive 自動化兩階段歸檔與安全清理 SOP
- **Cron Job 腳本**：每日 00:00 與 04:00 透過 GitHub Actions 或 Cloudflare Workers 觸發。
- **執行流程**：
  1. **階段一 (00:00 歸檔與軟刪除)**：
     - 撈出昨日未歸檔對話：`SELECT * FROM messages WHERE created_at < CURRENT_DATE AND is_archived = FALSE`。
     - 打包上傳 GDrive 備份檔 `chat_backup_YYYYMMDD.json.gz`。
     - GDrive 驗證 HTTP 200 後，標記軟刪除：`UPDATE messages SET is_archived = TRUE, archived_at = NOW() WHERE created_at < CURRENT_DATE`。
  2. **階段二 (04:00 非尖峰物理刪除)**：
     - 清除已過 7 天緩衝期之軟刪除資料：`DELETE FROM messages WHERE is_archived = TRUE AND archived_at < NOW() - INTERVAL '7 days'`，徹底兼顧備份安全性與熱庫容量控制 (< 100MB)。

## 五、 系統自我修復與殭屍清理 (Presence & Zombie Cleaning)

### 1. 三重殭屍使用者清理機制 (Zombie User Expiration & Cleaning)
- **短週期心跳過期 (10 秒過期)**：`pairing_queue` 表維護 `last_ping_at` 欄位，前端在等待配對時每 4 秒發送一次 Ping。RPC 配對時自動排除超過 10 秒未 Ping 的帳號 (`last_ping_at > NOW() - INTERVAL '10 seconds'`)。
- **`sendBeacon` 離線退列**：使用者關閉/切換分頁時透過 `navigator.sendBeacon()` 主動自 `pairing_queue` 退列。
- **8 秒 P2P 握手逾時自動重新配對 (Handshake Timeout)**：配對成功通知發送後，若 8 秒內雙方未完成 WebRTC P2P Data Channel 握手（狀態未轉為 `open`），前端自動宣告握手失敗，將線上用戶無縫重新送回佇列，並剔除離線端。

### 2. 配對輪詢與漸進式擴圈驗收規則（2026-08 修訂）

- 使用者進入等待池後，前端必須每 4 秒重新呼叫一次原子配對 RPC；只更新 `last_ping_at` 不算完成配對輪詢。
- 0–10 秒使用使用者選定距離；10–30 秒時，近距離模式自動擴大為原半徑 2 倍；等待滿 30 秒後切換為不限距離，以避免不同距離偏好的使用者永久互斥。
- 每次重試仍須由 `fn_match_user()` 使用 `FOR UPDATE SKIP LOCKED` 完成，禁止由前端自行建立房間。
- 配對成立時，資料庫須將 Haversine 計算結果寫入 `matches.distance_km`；聊天室僅能讀取此計算結果，不得取得對方原始經緯度。
- 驗收案例：一方選擇 5 km、另一方選擇「越遠越好」，若意圖相同且皆在線，最遲應在 30 秒擴圈後進入同一房間，不得持續等待數分鐘。

### 3. 資料真實性原則（2026-08 修訂）

- 行為資料只能由真實操作產生，不得為展示畫面寫入假使用者、假配對、假訊息或假統計。
- 話題分類與話題卡屬系統策展內容，必須透過可重複執行的 SQL seed 寫入正式資料表。
- 前端不得以硬編碼 fallback 偽裝資料庫已有內容；資料載入失敗或空表時必須顯示明確錯誤。
