# 04. 部署運維與擴展性手冊 (詳細展開版)

本手冊定義了系統從開發到上線的完整流程，並針對 1000 人 CCU 甚至未來 10,000 人併發的場景提供擴展藍圖，確保系統在長期運作下的穩定與可維護性。

---

## 一、 自動化部署與環境管理 (CI/CD)

### 1. 三層環境架構
- **Development (本地)**：使用 `supabase start` 在 Docker 容器中運行。
- **Staging (測試)**：用於功能驗證與壓力測試，配置與生產環境 1:1 鏡像。
- **Production (生產)**：正式對外服務。

### 2. 現階段部署策略與未來的預備架構 (Deployment & Readiness Strategy)
- **現階段唯一部署標的：GitHub Pages**
  - 目前所有開發、測試與測試營運**只發布於 GitHub Pages**，暫不使用或註冊 Cloudflare。
  - **GitHub Actions 自動化**：配置 `.github/workflows/deploy.yml`。每次 `push` 至 `main` 分支時，觸發 `npm run build` 生成 `out/` 靜態目錄，並透過 `actions/deploy-pages` 自動發布。
- **未來無痛轉移與雙部署預備規範 (Cloudflare-Ready Standards)**
  - 開發階段即設計好「雙平台相容格式」，確保未來某天若需要將專案發布至 Cloudflare Pages 時，**完全不需要修改任何一行專案程式碼**，即可直接雙邊部署。

### 3. 雙平台相容架構開發規範 (Dual-Platform Compatibility Standards)
- **純靜態解耦 (Static Export Decoupling)**：架構必須嚴格維持全靜態導出 (`output: 'export'`)，禁止相依任何獨有平台伺服器特有功能。
- **動態路徑適應 (Dynamic BasePath Adaptation)**：
  - GitHub Pages 部署通常位於專案子目錄 (如 `https://username.github.io/chat-repo/`)。
  - Cloudflare Pages / 自訂網域通常位於根目錄 (如 `https://chat.example.com/`)。
  - 前端路由與靜態資源引用的 `basePath` 必須根據環境變數 `NEXT_PUBLIC_BASE_PATH` 自動彈性切換，確保程式碼完全不需要改動即可在兩個平台無縫運作。

### 4. 環境變數與 Secrets 的雙平台相容讀取機制 (Universal Env & Secrets Standard)
- **統一命名規範**：所有需暴露給前端的環境變數一律使用 `NEXT_PUBLIC_` 首綴（例如：`NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY`, `NEXT_PUBLIC_IMGBB_API_KEY`）。
- **關鍵環境變數項目**：
  - `IMGBB_API_KEY`: ImgBB 主圖床 API 金鑰（置於根目錄 `.env`，嚴禁寫死在程式碼中）
  - `IMGBB_UPLOAD_URL`: ImgBB 上傳 API 端點 (`https://api.imgbb.com/1/upload`)
  - `VITE_SUPABASE_URL` / `NEXT_PUBLIC_SUPABASE_URL`: Supabase 專案 URL
  - `VITE_SUPABASE_ANON_KEY` / `NEXT_PUBLIC_SUPABASE_ANON_KEY`: Supabase 公開匿名 Key
- **多平台 Secrets 注入標準**：
  1. **本地開發 (Local)**：開發前必須確保讀取專案根目錄 `.env` 檔案。
  2. **GitHub Pages (CI/CD)**：設定於 GitHub Repository Secrets 中，在 GitHub Actions 執行 `npm run build` 時自動寫入構建環境。
  3. **Cloudflare Pages (Production)**：在 Cloudflare Dashboard 的 "Environment variables" 控制台直接設定相同名稱的變數，在 Cloudflare Pages Build 階段自動注入。
- **統一環境變數解析封裝層 (`lib/env.ts`)**：
  - 專案內部建立 `lib/env.ts` 抽象層，負責集中讀取 `process.env.NEXT_PUBLIC_*` 與 `.env` 變數。
  - 包含型別檢查與預設值 Fallback 機制，確保無論在本地、GitHub Actions 還是 Cloudflare Pages 打包時，均能提供防錯校驗，防範變數缺失導致打包失敗。

### 5. 資料庫遷移 (Migrations)
- 透過 `supabase db push` 將 SQL 變更同步至雲端。
- 嚴禁手動在 Supabase Dashboard 修改 Schema，所有變更必須透過 Migration 檔案版本化。

## 二、 1000 人併發下的運維監控系統

### 1. 全方位監控指標 (Metrics)
- **資料庫層面**：
  - `Connection Count`：監控 PgBouncer 的連線佔用率。
  - `Transaction Latency`：配對 SQL 的執行時間必須控制在 100ms 內。
- **伺服器層面 (Edge Functions)**：
  - `Invocation Count` 與 `Failure Rate`。
  - `Execution Duration`：平均回應時間應低於 200ms。
- **前端層面**：
  - `Web Vitals` (LCP, FID, CLS)。
  - `WebSocket Connection Success Rate`。

### 2. 錯誤追蹤與日誌
- **Sentry 整合**：捕獲前端 Runtime Error 與 Edge Function 崩潰日誌，並自動關聯至具體的 Release 版本。
- **Log Management**：使用 Supabase Log Explorer 設定過濾器，自動偵測異常高的 401 (Unauthorized) 或 429 (Too Many Requests) 錯誤。

## 三、 災難恢復與冷資料歸檔 SOP (Google Drive Archive)

### 1. 每日 Google Drive 自動備份與兩階段清理 SOP
- **自動化觸發**：每日 00:00 與 04:00 透過 GitHub Actions 或 Supabase Edge Function 觸發 Python / Node.js 歸檔腳本。
- **作業步驟**：
  1. **階段一：00:00 備份上傳與軟刪除標記**：
     - **Dump 資料**：連線 Supabase 撈出昨日全量未歸檔紀錄 `SELECT * FROM messages WHERE created_at < CURRENT_DATE AND is_archived = FALSE`。
     - **打包壓縮**：生成 `YYYY-MM-DD_chat_archive.json.gz`。
     - **Drive API 上傳**：使用 OAuth2/Service Account 上傳至 2TB Google Drive 指定目錄。
     - **軟刪除標記**：確認 GDrive 回傳成功碼 (HTTP 200) 後，執行 `UPDATE messages SET is_archived = TRUE, archived_at = NOW() WHERE created_at < CURRENT_DATE`。**絕不在此時直接實施物理刪除**，預留 7 天緩衝期防範 GDrive API 假性成功或檔案毀損。
  2. **階段二：04:00 非尖峰實體刪除**：
     - 於凌晨低流量時段執行 `DELETE FROM messages WHERE is_archived = TRUE AND archived_at < NOW() - INTERVAL '7 days'`。
     - **嚴禁使用 `TRUNCATE TABLE messages`**（防範 PostgreSQL 獲取 ACCESS EXCLUSIVE 強制排他鎖引發鎖表與崩潰）。
- **數據效益**：7 天緩衝期僅額外佔用約 150-200MB 熱庫容量，Supabase 500MB 免費資料庫用量完全可控，且備份資料安全性達 100%。

### 2. 應急預案 (SOP)
- **資料庫鎖死**：若監控顯示死鎖，管理員透過預先準備的 SQL 腳本執行 `pg_terminate_backend` 強制中斷異常進程。
- **流量暴增**：若 CCU 突破 2000 導致延遲，開啟「流量分流模式」，將部分配對請求導向簡化版的緩存查詢。

## 四、 未來擴展性藍圖 (Scalability Roadmap)

當在線人數從 1,000 成長至 10,000+ 時，需執行以下優化：

### 1. 配對引擎移轉 (Redis Matching)
- **現狀**：基於 PostgreSQL 的 `SKIP LOCKED`。
- **萬人方案**：引入 **Upstash Redis**。將配對池移入 Redis 的 `Sorted Set`。
  - **優點**：讀寫延遲從 50ms 降至 2ms，且能極大化降低資料庫負擔。

### 2. WebRTC 穿透與中繼伺服器 (STUN/TURN Early Readiness)
- **初上線機制 (1,000 人 CCU 初期備妥)**：在行動網路（如 4G/5G CGNAT）環境下，純免費 STUN 伺服器的 P2P 穿透失敗率極高。系統**不等到 10,000 人 CCU 才規劃**，而是於 1,000 人 CCU 初期即預先部署備妥企業級 **TURN Server 中繼方案 (如 Coturn / Cloudflare Calls / Twilio)**，當 P2P 穿透失敗時秒級降級至 TURN 中繼，保障極端網路環境下的連線成功率 > 99.9%。

### 3. 全球化邊署 (Global Distribution)
- 透過 Vercel 與 Supabase 的 Edge 節點，將資料存儲與運算靠近使用者所在的地理區域，降低跨國連線的延遲。

## 五、 管理工具 (Admin Dashboard)

建立一個僅限內部使用的後台介面：
- **實時監控面板**：顯示當前在線人數、配對成功率、訊息發送頻率。
- **舉報審核系統**：列出被舉報次數最高的使用者，供人工介入封鎖。
- **系統公告推送**：一鍵發送 WebSocket 公告訊息給所有在線使用者。
